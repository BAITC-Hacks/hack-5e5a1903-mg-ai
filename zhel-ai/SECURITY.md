# Политика безопасности

## Как сообщить об уязвимости

Не создавайте публичный issue. Напишите команде проекта или используйте
GitHub Private Vulnerability Reporting. Во время хакатона об инциденте нужно
дополнительно сообщить организаторам или в штаб кибербезопасности, как требуют
[правила соревнования](../rules/README.md).

## Принятые меры

Здесь перечислено только то, что реально сделано в этом репозитории.

- Секреты передаются исключительно через переменные окружения. Перечень нужных
  переменных лежит в `.env.example` без значений, сам `.env` в `.gitignore`.
- В коде нет захардкоженных ключей и токенов. Строка подключения к БД не хранится,
  а собирается из отдельных переменных окружения. Единственный пароль в исходниках —
  значение по умолчанию для демонстрационного администратора, см. раздел
  «Осознанно принятые риски».
- Пароли хранятся хешами Argon2, схема хеширования вынесена в `src/core/security.py`.
  Тест проверяет, что хеш отличается от пароля и что он солится.
- Доступ к защищенным эндпоинтам только по JWT. Access и refresh токены различаются
  полем `type`, и refresh-токен не принимается вместо access. Это покрыто тестом.
- Ответ на неверный пароль и на несуществующий email одинаковый, чтобы не раскрывать
  существование учетной записи. Покрыто тестом.
- Входные данные валидируются на границе API схемами Pydantic, ошибки валидации
  возвращаются в едином формате без деталей внутреннего устройства.
- В окружении `production` текст внутренней ошибки не отдается клиенту.
- Хук `detect-private-key` в `.pre-commit-config.yaml` не дает закоммитить приватный ключ.
- Контейнер backend работает не от root, а от отдельного пользователя `appuser`.
- Зависимости проверяются на известные уязвимости перед каждым мерджем командой
  `make audit`: `pip-audit` по зафиксированным версиям из `backend/uv.lock` и
  `npm audit` для frontend. Та же проверка идет автоматически в каждом pull request
  и раз в сутки по расписанию, workflow `.github/workflows/audit.yml`.
  Подробности: [docs/dependency-audit.md](docs/dependency-audit.md).
- Версии зависимостей зафиксированы в `uv.lock`, образ собирается с `uv sync --frozen`,
  поэтому в сборку не может попасть неожиданная версия пакета.
- Прямой push и коммит в `main` запрещены. Изменения попадают туда только через
  pull request, force-push и удаление ветки запрещены защитой ветки.

## Осознанно принятые риски

### Демонстрационный администратор admin/admin

`backend/src/scripts/seed.py` без переменных окружения создает пользователя с логином
`admin` и паролем `admin`, эти же значения лежат в `.env.example`. Это сделано намеренно:
стенд хакатона должен открываться у судьи с первого раза, без раздачи учетных данных
в описании решения и без лишнего шага в инструкции запуска.

**Это не безопасная конфигурация и не годится ни для чего, кроме показа.** Пара
admin/admin общеизвестна, ограничения частоты попыток входа в проекте нет, так что
подбором такой пароль не защищен вовсе.

Как поменять: задать `SEED_ADMIN_EMAIL` и `SEED_ADMIN_PASSWORD` в `.env` **до первого**
`make seed`. Скрипт идемпотентен и существующему пользователю пароль не переписывает,
поэтому на уже засеянной базе смена переменных даст второго пользователя, а не новый
пароль первому. При запуске с паролем по умолчанию скрипт пишет об этом предупреждение
в лог.

Что защищает даже такой стенд: пароль все равно хранится хешем Argon2, эндпоинты
прогноза закрыты Bearer-токеном, публичной регистрации нет.

## Чего пока нет

- Нет эндпоинта обмена refresh-токена, поэтому отзыв токенов не реализован.
- Нет ограничения частоты попыток входа.
- Dependabot не подключен, обновления зависимостей не приходят автоматически.
- Образ Docker не проверяется на уязвимости системных пакетов автоматически.
