# ADR 0004: Тесты на SQLite в памяти, приложение на PostgreSQL

## Статус

Принято

## Контекст

Нужны тесты, которые проходят в CI на каждый push и при этом не требуют долгой
подготовки окружения. Приложение работает на PostgreSQL. Вариантов два: поднимать
в CI сервис с PostgreSQL или прогонять тесты на SQLite в памяти.

## Решение

Тесты используют `sqlite+aiosqlite` в памяти на одном соединении через `StaticPool`.
Таблицы создаются из тех же моделей SQLAlchemy вызовом `Base.metadata.create_all`.
HTTP-тесты идут через `httpx.ASGITransport`, который не выполняет lifespan, поэтому
приложение в тестах не обращается к настоящей БД. Зависимость `get_db` подменяется
на тестовую сессию.

Чтобы те же модели поднимались на SQLite, тип первичного ключа в
`src/core/base_model.py` объявлен как `BigInteger().with_variant(Integer, "sqlite")`.
В SQLite столбец `BIGINT` не является алиасом rowid, поэтому автоинкремент на нем
не работает и вставка без явного `id` падала бы. На PostgreSQL тип остался `BIGINT`.

## Альтернативы

- **Сервис PostgreSQL в CI.** Точнее повторяет продакшн и поймал бы специфику диалекта.
  Отпало: дольше в прогоне, больше подвижных частей в workflow, а для локального
  запуска потребовало бы отдельную тестовую базу, чтобы не удалять таблицы рабочей.
- **Мокать сессию БД.** Быстро, но тогда тесты не проверяют ни модели, ни запросы,
  и ломаются при любом рефакторинге.
- **Тестировать только чистые функции без БД.** Не покрыло бы сервис аутентификации,
  где и живет основная логика.

## Последствия

Плюс: полный прогон занимает около двух секунд, CI не нуждается в сервисах, тесты
работают у каждого разработчика без поднятого docker-стека.

Минус: расхождения диалектов SQLite и PostgreSQL тесты не поймают. Поведение, которое
зависит от конкретной БД, проверяется на запущенном стеке вручную, а миграции
применяются через `docker compose exec backend alembic upgrade head`. Сами миграции
тесты не проверяют, поскольку таблицы создаются напрямую из моделей.
