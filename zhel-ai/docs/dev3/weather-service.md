# Сервис погоды

HTTP-сервис dev3 (#46, контракт согласован в #37). Отдает архивные прогнозы погоды по точке
ВЭС «Шелек» ровно в том виде, в каком они были доступны на момент прогноза, и почасовую
историю турбин. Вызывает его backend dev1 по `WEATHER_SERVICE_URL`, frontend напрямую не ходит.

- Полная схема: [weather-openapi.json](weather-openapi.json). Файл генерируется из кода,
  тест `backend/tests/weather_service/test_openapi.py` не дает ему устареть.
- Swagger у запущенного сервиса: `/docs`.
- Код: `backend/src/weather_service/`. Это тонкий слой над `src.forecast.weather` (`AsOfStore`)
  и `src.forecast.dataset` (`load_scada`), своей логики выбора прогонов в нем нет.

## Запуск

В составе стека сервис `weather` поднимается из `docker-compose.yml` вместе с остальными:

```bash
docker compose up -d --build weather backend
```

Это тот же образ, что у backend, с другой командой (`uvicorn src.weather_service.main:app`).
`data/` подключен только на чтение как `/data`, `DATA_DIR=/data`. Секреты из `.env` сервису
не нужны, поэтому `env_file` у него нет. Healthcheck идет на `/health`, и backend стартует только
после того, как сервис погоды здоров (`depends_on: condition: service_healthy`). Backend ходит
в него по сети compose, адрес `WEATHER_SERVICE_URL=http://weather:8000`. Наружу опубликован
порт `WEATHER_PORT` (8020 в слоте 0), только ради Swagger: `http://localhost:8020/docs`.

Без Docker, из папки `backend`, сеть и Postgres не нужны:

```bash
uv run uvicorn src.weather_service.main:app --port 8020
```

Данные читаются из `DATA_DIR`, пустое значение означает `data/` в репозитории: кэш прогнозов
`data/nwp/`, SCADA — два CSV в `data/`. Всё загружается один раз на старте, около 5 секунд,
дальше только читается.

## Эндпоинты

| Метод и путь | Что отдает | Кому |
|---|---|---|
| `GET /health` | `ok` или `degraded`, число прогонов и период кэша по источникам, часов SCADA | healthcheck |
| `GET /sources` | реестр источников: тип API, шаг, задержка публикации и ее основание, высоты ветра, пустые колонки, период архива, состав ансамбля, MAE ветра | страница «Погода» |
| `GET /nwp?source=&as_of=[&from=&to=]` | строки «час × источник», опубликованные не позже `as_of` | `POST /predict` у ML-сервиса, страница «Погода» |
| `GET /runs?as_of=[&issue_time=&source=&status=]` | прогоны, покрывающие горизонт выпуска, со статусом `used`, `stale`, `after_as_of` | страница «Погода» |
| `GET /runs?from=&to=[&source=]` | события «прогон стал доступен» в `(from, to]` | пересчет выпуска агентом |
| `GET /scada?from=&until=[&turbine=]` | часы SCADA в `[from, until)` | факт для бэктеста |

Соглашения:

- время передается в ISO 8601, в UTC, с `Z`. Время без пояса дает 422, время с другим
  смещением переводится в UTC. Пустое значение передается как `null`;
- источники: `ifs`, `ifs025`, `gfs`, `icon`, `gem`, `ensemble`, несколько через запятую;
- окно `/nwp` по умолчанию равно горизонту выпуска `as_of + 1 ч … as_of + 48 ч`, то есть ровно
  тому, что ждет `POST /predict`. Окно не больше 168 ч, у `/scada` и событий `/runs` —
  не больше 31 суток;
- `lead_h` в строке `/nwp` считается от запуска прогона, а не от выпуска;
- в каждой строке `/nwp` есть ветер хотя бы на одной высоте и `t2m`. Строка прогона без них
  считается отсутствующей, и на этот час берется прогон старше, опубликованный к `as_of`.
  Нет такого прогона — `NO_RUN_AVAILABLE` для этого источника. Так устроен и фолбэк ветра
  в `AsOfStore` (#62). Температура нужна backend: на ней стоит проверка на обледенение,
  и `t2m` в его `NwpRow` обязательна. В кэше `ifs` таких строк 216.

## Источники

Значения из `GET /sources` на закоммиченном кэше:

| source | Тип | Шаг | Задержка | Высоты ветра | Всегда `null` | Кэш |
|---|---|---|---|---|---|---|
| `ifs` | single_runs | 6 ч | 7,5 ч | 80, 100, 120 | `ws10` | 15.03.2024 – 03.03.2026 |
| `ifs025` | previous_runs | 6 ч | 10 ч, допущение | 100 | `ws10`, `ws80`, `ws120`, `gust10` | 06.03.2024 – 01.03.2026 |
| `gfs` | previous_runs | 6 ч | 7 ч | 80, 100, 120 | `ws10` | 16.02.2024 – 01.03.2026 |
| `icon` | previous_runs | 6 ч | 8 ч, допущение | 80, 100, 120 | `ws10` | 16.02.2024 – 01.03.2026 |
| `gem` | previous_runs | 12 ч | 8 ч, допущение | 80, 120 | `ws10`, `ws100`, `wd100` | 16.02.2024 – 01.03.2026 |
| `ensemble` | ensemble | — | по участникам | 80 | `ws10`, `ws100`, `ws120` | 06.03.2024 – 01.03.2026 |

У `ifs` в кэше до 31.01.2026 только прогоны 12z и 18z, с 01.02.2026 все четыре. Подробности
о прогонах и пробелах в архиве — в [README.md](README.md).

**Ансамбль** — среднее `ifs025`, `gfs`, `icon`, `gem`. `ws80` — это ветер на высоте ступицы:
80 м, а если этой высоты нет, 100 или 120 м, приведенные к 80 м с показателем сдвига 0,14,
так же, как в ML-сервисе. `ws_spread` — стандартное отклонение между моделями (ddof=0),
`members` — какие модели дали значение на этот час. Время прогона и доступности берется
у самого позднего участника.

**Строки `ensemble` не отправляйте в `POST /predict` вместе со строками участников.**
ML-сервис сам усредняет источники, поэтому ансамбль учтется дважды. Для модели передаются
участники, а `ensemble` нужен странице «Погода».

Статусы прогонов для страницы «Погода»:

```bash
curl -s "localhost:8020/runs?source=ifs&as_of=2026-01-31T02:00:00Z&status=used"
# [{"source":"ifs","run_init_utc":"2026-01-30T18:00:00Z","available_at_utc":"2026-01-31T01:30:00Z",
#   "status":"used","lead_from_h":9,"lead_to_h":56,"hours_used":48}]
```

- `used` — прогон дал часы горизонта;
- `stale` — прогон опубликован к `as_of`, но на все его часы есть прогон свежее;
- `after_as_of` — прогон опубликован позже `as_of`. В `WeatherRun` backend этот статус
  называется `after_issue`, они соответствуют друг другу один к одному.

Для пересчета выпуска передается `issue_time` (горизонт) и более поздний `as_of` (что уже
вышло).

## Ошибки

Ошибка всегда приходит в конверте `{"error": {"code", "message", "details"}}`, как в backend.

| HTTP | `code` | Когда | Что делает backend |
|---|---|---|---|
| 404 | `NO_RUN_AVAILABLE` | у источника нет прогона, опубликованного к `as_of`, хотя бы на один час. `details`: `source`, `as_of_utc`, `missing_hours`, примеры часов. Из нескольких источников такие пропускаются и попадают в `missing`, а 404 бывает, только если данных нет ни у одного | берет следующий источник, выпуск получает флаг `degraded` |
| 422 | `UNKNOWN_SOURCE` | источника нет в реестре. `details.known` — список имен | ошибка вызова |
| 422 | `VALIDATION_ERROR` | нет параметра, время без пояса, час не с начала, `from` позже `to`, окно больше лимита, неизвестный статус | ошибка вызова |
| 500 | `LEAKAGE_GUARD` | в ответ попала строка с `available_at_utc > as_of`. Последняя проверка перед отдачей остановила ответ. Так быть не должно никогда | не публиковать выпуск, это баг dev3 |
| 503 | `DATA_UNAVAILABLE` | SCADA не загружена: нет файлов в `DATA_DIR` | факта нет, бэктест без него |
| 500 | `INTERNAL_ERROR` | всё остальное | как отказ сервиса |

## Как его читают соседи

- **Backend dev1** (`backend/src/modules/forecast/clients/weather.py`, `HttpWeatherSource`)
  спрашивает `GET /nwp?source=&as_of=&from=&to=` по одному источнику и берет `rows` из ответа,
  и `GET /runs?as_of=&from=&to=` для пересчета. 404 `NO_RUN_AVAILABLE` у него штатный
  `WEATHER_NO_RUN`: агент берет следующий источник. Сервис не ответил совсем — агент уходит
  на запасной путь, `AsOfStore` в процессе backend, и пишет это в журнал решений.
- **ML-сервис dev2** получает строки `rows` в `POST /predict` как есть, по схеме `WeatherRow`.

Совместимость проверяет `backend/tests/weather_service/test_compat.py`: ответы валидируются копиями
`NwpRow`, `NwpResponse`, `RunRow` backend и `WeatherRow` ML-сервиса
(`tests/weather_service/consumer_schemas.py`), а 28 выпусков февраля прогоняются по закоммиченному
кэшу. Поменялась схема у соседа — обновляется копия, и тест показывает, отвечает ли ей сервис.

## Проверка

```bash
cd backend
uv run pytest tests/weather_service                  # синтетический кэш и закоммиченный кэш февраля
uv run python -m src.weather_service.export_openapi  # пересобрать weather-openapi.json после изменения схем
```

Тесты проверяют формы ответов; что ни одна строка `/nwp` не опубликована позже `as_of`
на разных моментах, включая границу публикации прогона; совпадение с `AsOfStore`; ансамбль;
фолбэк на прогон старше для часов без `t2m`; статусы `/runs` и события; совместимость со схемами
backend и ML-сервиса; ошибки `NO_RUN_AVAILABLE`, `UNKNOWN_SOURCE`, `VALIDATION_ERROR`,
`LEAKAGE_GUARD` и `DATA_UNAVAILABLE`.

## Известные ограничения

- Пересчет. `POST /predict` у ML-сервиса отклоняет строки с `available_at_utc > issue_time_utc`,
  поэтому строки на более поздний `as_of` он сейчас не примет. Это граница между backend
  и ML-сервисом, сервис погоды ее не меняет.
- Направление ветра у `gem` есть только на 80 м, в строке `/nwp` поле `wd100` у него `null`.
- SCADA заканчивается 31.01.2026 17:00 UTC. Для февраля `/scada` отдает пустой список.
