## 1. Вердикт: 🟡 → 🟢 при урезанном scope

За 4 часа реально сделать честную as-of систему на **двух источниках Open-Meteo** с закоммиченным кэшем, простой моделью (LightGBM + физическая кривая мощности), тремя бейзлайнами, агентом-state machine с логом решений и автоматическим аудитом утечек. ## 3. Архитектура

```
 события (виртуальные часы UTC)            ┌──────────── AGENT (state machine) ────────────┐
 RunAvailable(model, init, available_at) ─▶ │ SENSE → FETCH → VALIDATE → PREPARE → PREDICT │
 IssueTime(ежедневно 10:00 Астана)       ─▶ │   ↑        │fail→FALLBACK       │          │
                                            │   └── DECIDE ← EVALUATE ◀─────────┘          │
                                            │         │publish?                             │
                                            └─────────┼─────────────────────────────────────┘
 AsOfStore (единственная дверь к данным)             ▼
  ├─ om_single_ifs  (точный прогон, available_at = init+7:30)   outputs/forecasts/issue=…Z/
  ├─ om_prev_gfs    (previous_dayN, available_at = init+7:00)       forecast.csv + manifest.json
  └─ scada          (≤ cutoff; в тестовом месяце — пусто)        outputs/decisions.jsonl, reports/
```

### As-of «машина времени» (ядро оценки по «работоспособности»)
- **Виртуальные часы:** `now` = момент выпуска T0 (UTC). В симуляции сеть выключена, данные берутся только из кэша.
- **AsOfStore.get(model, as_of, valid_times)** возвращает строки, у которых `available_at ≤ as_of`, с колонками `init, lead, available_at, source`. Фильтр идёт по **времени доступности**, а не по init. Задержки консервативные, из замеров выше: IFS через OM — init+7:30, GFS через OM — init+7:00, запас около 30 мин.
- **Выбор прогона для каждого часа горизонта:**
  - Single Runs (IFS): берём последний прогон R, у которого `init + 7:30 ≤ T0`. Пример: T0 = 31.01 05:00Z (10:00 Астаны) → 00z за 31.01 ещё недоступен (07:30), поэтому берётся **18z за 30.01** (доступен в 01:30), заблаговременность для +1…+48 ч — 12…59 ч.
  - Previous Runs (GFS): для каждого t берём `N* = min{N : floor_6h(t − 24N) + 7:00 ≤ T0}`. Пример: t = 01.02 00:00Z → N=1 даёт прогон 31.01 00z, он доступен в 07:00 > T0, не подходит; N=2 даёт 30.01 00z, подходит, lead 48 ч. **`previous_day1` вслепую не используем.**
  - Обучение идёт **той же функцией**: для каждого исторического дня симулируется T0 = 05:00Z, и признаки строятся через `AsOfStore(as_of=T0)`. Так распределение заблаговременностей в train и serve совпадает (нет train/serve skew).
- **SCADA:** в валидационных фолдах и в тесте данные обрезаются на начале месяца, как у организаторов (в феврале факта нет). Поэтому модель не использует лаги SCADA, persistence остаётся только бейзлайном.
- **Автоаудит утечек (`make audit`, тесты):**
  1. `max(available_at всех входов) ≤ issue_time` для каждого manifest;
  2. **canary/poison**: всё, что стало доступно после T0, заменяем мусором, прогоняем выпуск заново → выход должен совпасть **побайтно**;
  3. `test_prevday_mapping`: правило floor_6h сверяется с закэшированной выборкой Single Runs;
  4. ERA5 и Historical Forecast API разрешены только в `diagnostics/` (проверка TZ); pipeline их не импортирует (тест на импорт).

## 4. Данные погоды (урезанный план)
- **Основной источник:** Open-Meteo **Single Runs `ecmwf_ifs`**, 4 прогона в сутки с 2024-03-15 по 2026-02-28. Это около 2 800 запросов по 1 точке, 54–72 ч, около 12 переменных; за 5–10 минут укладывается в лимит. Переменные: ветер 10/80/100/120 м, направление 100 м, порывы, T2m, RH, давление у поверхности (→ плотность ρ = p/(R·T)), BLH.
- **Резерв и второй член ансамбля:** Previous Runs `gfs_global`, `previous_day1..3` для тех же переменных, с 2024-02-17. Около 25 запросов по 1 месяцу.
- **Кэш:** `data/cache/nwp/{source}/{yyyy-mm}.parquet` плюс `SHA256SUMS`. Для одной точки это единицы МБ, поэтому **коммитим в репозиторий**, и `make demo` работает без сети.
- SCADA с марта 2023 по март 2024 без NWP тоже полезна: на ней строится **эмпирическая кривая мощности**, для которой NWP не нужен.

## 5. ML (минимум, который защищается)
- **SCADA:** выравниваем шаг до часа. Проверяем TZ по кросс-корреляции T и ветра с IFS (лаги −3…+3 ч, отдельно до и после 01.03.2024), правило TZ фиксируем в `site.yaml`. Флаги: простой (P≈0 при v 4–20 м/с), полкапа (одна турбина), curtailment (плато P<0.95 при v>11), подозрение на обледенение (T≤1 °C и P ниже кривой), замёрзший датчик (v постоянна ≥3 ч), дубликаты и пропуски. Флаги убираем из обучения кривой, но метрики считаем по всем часам.
- **Бейзлайны:** (1) persistence; (2) климатология месяц×час; (3) **NWP + паспортная кривая** GW109/2500 (cut-in 3, номинал 10,3, cut-out 25 м/с) с поправкой на плотность v·(ρ/1.225)^(1/3).
- **Модель:** LightGBM (objective `l1`, `deterministic=True`, `seed`) на признаках IFS (+ GFS): v80, v100, v120, сдвиг α, sin/cos направления, порывы, ρ, T, BLH, lead, час, день года, расхождение IFS−GFS, **PC_emp(v_hub, ρ)** (физический признак). Монотонное ограничение по v. Клип в [min_hist, 1.0].
- **Интервалы:** эмпирические квантили остатков по корзинам lead (1–24 / 25–48) и уровню прогноза, сделано на OOF. Метрика — покрытие P10–P90.
- **Валидация:** rolling-origin в том же as-of режиме: **янв-2026** (train ≤ 31.12.2025) и **фев-2025** (train с 15.03.2024 по 31.01.2025). Метрики: nMAE и nRMSE в % от 5 МВт, bias, skill к трём бейзлайнам, отдельно по часам 1–24 и 25–48.

## 6. Агент: явная state machine плюс опциональный OpenAI
- **Решения, которые агент принимает сам** (пишутся в `decisions.jsonl` с `reason_code`):
  - `FALLBACK`: IFS не пришёл или битый → GFS previous runs → предыдущий доступный прогон → климатология.
  - `RERUN`: по событию «новый прогон доступен (as-of)» агент пересчитывает; `PUBLISH_NEW_VERSION` при |ΔE_сутки| > 3% или max|ΔP| > 10% Pn, иначе `NO_MATERIAL_CHANGE`.
  - `VALIDATE_FAIL`: NaN, выход за диапазон, «застывший» прогон, скачок между прогонами, IFS vs GFS > 5 м/с → понижение веса или исключение.
  - `FLAGS`: риск cut-out (v>25), риск обледенения (T≤1 °C и RH>90%), резкие изменения (>40% Pn за 3 ч).
  - `REPORT`: сводка для диспетчера.
- **LLM:** `LLM_MODE=offline|replay|openai`. По умолчанию `offline` — шаблонный отчёт; `replay` — ответы из закоммиченных `llm_cassettes/*.json`; `openai` — нужен `OPENAI_API_KEY`, модель задаётся через `OPENAI_MODEL`. LLM только пишет и объясняет, **числа не меняет**. Ключевые функции без ключа работают полностью.
- Одна симуляция февраля — это около 28 × 5 событий (4 прогона IFS + выпуск). Видно, что «повторный расчёт при обновлении входных данных» происходит по реальным временам выхода прогонов.

## 9. Фишка
**«Машина времени с canary-тестом»:** каждый файл прогноза несёт manifest с доказательством того, какие прогоны были известны и когда. Тест подменяет все данные «из будущего» мусором, и выход совпадает побайтно. Задержки публикации не придуманы, а измерены по S3 LastModified и `meta.json`. AI-судья и жюри проверяют отсутствие утечки одной командой `make audit`.
