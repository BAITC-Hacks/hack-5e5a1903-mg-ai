# ZHEL.ai — Agentic AI для прогноза выработки ВЭС

Кейс HackAlem AI. Почасовой прогноз выработки двух ветротурбин на 24–48 ч, который выпускает ИИ-агент. Агент сам проходит цикл: погода → подготовка → модель → прогноз → анализ → перерасчёт.

Файл `ZHEL Forecast.dc.html` — это интерактивный прототип дашборда. Все цифры в нём синтетические, их заменят реальные данные SCADA и архив погодных прогнозов. В `ZHEL Forecast Dark.dc.html` лежит прежняя тёмная версия.

## 1. Условия задачи

| | |
|---|---|
| Объект | 2 турбины. T1: 43.645150, 78.535604. T2: 43.643198, 78.538828. Алматинская обл., UTC+5 |
| Данные SCADA | 01.03.2023 – 31.01.2026, шаг 1 ч: `timestamp`, `wind_speed`, `active_power_norm`, `ambient_temp` |
| Тестовый период | 01.02.2026 – 28.02.2026 |
| Выход | 48 значений с шагом 1 ч на каждую точку прогноза T. Нужны P10, P50 и P90 |
| Ретро-прогноз | 28 запусков, T = 31.01 … 27.02, каждый день в 18:00 UTC+5. Прогноз охватывает следующие двое суток 00:00–23:00 |
| Главное ограничение | Использовать только информацию, доступную на момент T (**as_of**). Никакой фактической погоды после T |

Критерии оценки (100 баллов): соответствие задаче и работоспособность (25), техническая реализация (25), README и воспроизводимость (25), ценность (15), оригинальность (10).

## 2. Архитектура

```
Триггеры (планировщик прогонов NWP, replay, ручной запуск)
   ↓
Агент (LLM-планировщик + граф LangGraph, 6 узлов, условное ребро анализ → перерасчёт)
   ↓
Инструменты (детерминированные Python-функции, у каждой аргумент as_of)
   ↓
Данные (SCADA в Parquet, архив NWP с issued_at, версии прогнозов, метрики в MLflow, DuckDB)
   ↓
Выход (REST API /forecast, дашборд, CSV, отчёт агента на русском)
```

**Принцип:** LLM только планирует шаги и интерпретирует результаты. Все числа считают инструменты, поэтому при одних входах прогноз всегда одинаковый.

### 2.1 Граф агента

| # | Узел | Что делает | Инструменты |
|---|---|---|---|
| 1 | Погода | Берёт прогнозы 4 моделей NWP по координатам. Использует только прогоны с `available_at ≤ T` | `get_weather_forecast` |
| 2 | Подготовка | SCADA до T, MOS-коррекция ветра, признаки | `get_scada_history`, `build_features` |
| 3 | Модель | Квантили P10/P50/P90 | `predict` |
| 4 | Прогноз | Публикует версию v1 | `publish_forecast` |
| 5 | Анализ | Проверки: разброс моделей, рампы, отсечка 25 м/с, границы 0–100% | `analyze_forecast` |
| 6 | Перерасчёт | Запускается по триггеру: веса по точности за 14 дней, интервал шире в 1,2 раза, версия v2 | `predict`, `publish_forecast`, `write_report` |

**Триггеры перерасчёта**
- вышел новый прогон NWP (00/06/12/18 UTC);
- разброс моделей после +30 ч выше порога (в прототипе это медиана по февралю, ≈ 1,5 м/с);
- пришли новые данные SCADA или найдены пропуски;
- ошибка вчерашнего прогноза в 1,5 раза выше нормы.

### 2.2 Инструменты (контракты)

```python
get_weather_forecast(model: str, lat: float, lon: float, as_of: datetime) -> DataFrame
    # hourly: wind_speed_100m, wind_direction_100m, temperature_2m, wind_gusts_10m
    # assert run.available_at <= as_of
get_scada_history(until: datetime, window: str = "30d") -> DataFrame
build_features(weather, scada, hub_height=100, mos=True, air_density=True) -> DataFrame  # 48 × ~23
predict(features, model="lgbm_quantile_v3", q=(0.1, 0.5, 0.9), weights=None, widen=1.0) -> DataFrame
analyze_forecast(forecast, weather, checks=["spread","ramps","cut_out","bounds"]) -> dict
publish_forecast(forecast, version: int) -> str
write_report(forecast, analysis, lang="ru") -> str
```

## 3. Погодные данные (важно)

- Источник — Open-Meteo, бесплатно. Модели: `ecmwf_ifs025`, `gfs_seamless`, `icon_global`, `gem_global`.
- Точка запроса — середина между турбинами (≈ 43.6442, 78.5372). Турбины стоят в ~330 м друг от друга, это одна ячейка сетки.
- **Ловушка:** Historical Forecast API склеивает первые часы каждого прогона. Для горизонта 24–48 ч это утечка будущего, и точность получится завышенной.
- **Решение:** брать Previous Runs API (`*_previous_day1`, `*_previous_day2`) или сырые прогоны GFS и ECMWF Open Data с явным временем выпуска.
- Задержка публикации прогона ≈ 6 ч. Для T = 18:00 UTC+5 (13:00 UTC) последний доступный прогон — 06Z того же дня.
- Архив хранится с полями `issued_at` и `available_at`, кэш — по ключу `as_of`.

```
GET https://previous-runs-api.open-meteo.com/v1/forecast
  ?latitude=43.6442&longitude=78.5372
  &hourly=wind_speed_100m,wind_direction_100m,temperature_2m,wind_gusts_10m
  &models=ecmwf_ifs025,gfs_seamless,icon_global,gem_global
```

## 4. ML-модель

1. **MOS:** линейная коррекция прогнозного ветра под измеренный ветер турбин, отдельно по каждой модели NWP.
2. **Ансамбль:** 4 источника смешиваются с весами по MAE ветра за последние 14 дней до T. Стартовые веса в прототипе: ECMWF 0.38, GFS 0.24, ICON 0.22, GEM 0.16.
3. **LightGBM-квантили:** отдельные модели для q = 0.1, 0.5 и 0.9.
4. **Физические ограничения:** мощность в пределах 0–1, 0 при ветре выше 25 м/с, P10 ≤ P50 ≤ P90. Эмпирическая кривая мощности подбирается по истории (в прототипе cut-in 3 м/с, номинал около 13,5 м/с).

**Признаки:** `wind_speed_100m` (ансамбль, в кубе), `wind_direction` (sin/cos), `temperature_2m`, `air_density`, `nwp_spread`, `lead_time`, `hour` (sin/cos), `doy` (sin/cos), `power_last_T`, `power_mean_24h`.

**Схема обучения (walk-forward):** обучение 03.2023–10.2025, валидация 11.2025–31.01.2026, тест — февраль 2026. Обучать только на данных до T.

---

## 5. Метрики и бэктест

- nMAE и nRMSE в % от установленной мощности. Считаются отдельно для D+1 (+6…+30 ч от T) и D+2 (+30…+54 ч).
- Покрытие интервала P10–P90 (цель ≈ 80%) и pinball loss.
- Базовые методы для сравнения: персистентность, климатология, кривая мощности на ECMWF, ансамбль NWP + кривая.
- Skill = 1 − nMAE_модели / nMAE_персистентности.
- `make replay` запускает 28 прогонов агента и сохраняет в `reports/` таблицу метрик, CSV прогнозов и логи агента.

Ориентиры из прототипа (синтетика, не цель): nMAE D+1 ≈ 12%, D+2 ≈ 19%, skill к персистентности ≈ 60%.

## 6. Дашборд: страницы и логика

Общая шапка:
- **день выпуска прогноза T** — бегунок 31.01–27.02 и стрелки;
- **статус агента** — «в работе / прогноз готов · v1 или v2»;
- кнопка **«▶ Replay 28 дней»** — автопроигрывание, ~1,6 с на день;
- кнопка **«Пересчитать»**.

При смене T пересчитываются все страницы, агент заново проходит цикл.

| Страница | Содержание |
|---|---|
| **Обзор** | Блок с крутящимися турбинами: скорость вращения = прогнозный ветер, при ветре ниже 3 м/с турбины стоят. Главный вывод простыми словами. KPI: средняя загрузка, пиковый час, часы ниже 10%, ожидаемая ошибка. График 24/48 ч: P50, полоса P10–P90, факт, ветер, подсказка при наведении. Ползунок **«что если»** сдвигает ветер на ±2 м/с и пересчитывает прогноз. Вывод агента с 4 проверками, сводка погоды, почасовая сетка, CSV |
| **Диспетчер** | Ползунок допустимого риска недовыработки 10–50%. Почасовая заявка на завтра в МВт: заявка = P10 + (q − 0.1) / 0.4 · (P50 − P10). График и таблица. KPI: заявка на сутки, ожидаемая выработка, доля часов с недобором в бэктесте, средний недобор в МВт·ч/сут |
| **Агент** | 6 этапов со статусами. Живой лог (TOOL / THINK / OK / WARN) с `as_of`. Триггеры, список инструментов, блок о защите от утечки будущего |
| **Бэктест** | KPI (nMAE D+1/D+2, nRMSE, skill). Прогноз против факта за февраль. Календарь 28 запусков, клик открывает день. Сравнение с базовыми методами, ошибка по горизонту 1–48 ч |
| **Погода** | Доступность прогонов NWP на T: используется / старее / опубликован после T. 4 модели и ансамбль на одном графике, таблица весов и MAE, предупреждение о ловушке с данными |
| **Модель** | 4 шага (MOS → ансамбль → LightGBM → физика), кривая мощности по SCADA, важность признаков (SHAP), схема walk-forward |
| **Объект** | Спутниковая карта (Esri) с T1 и T2, расстояние между ними, точка NWP. Прогноз по каждой турбине в МВт·ч. Поля SCADA, ссылки на Google Maps |
| **Архитектура** | Слои системы, структура репозитория, команды запуска, соответствие критериям |

Настройки прототипа: скорость лога агента, скорость replay, **мощность станции (сейчас 5 МВт, это допущение — нужно уточнить)**, стартовая страница.

Стиль: светлая тема, шрифты Onest и JetBrains Mono. Акцентные цвета: лаймовый `oklch(0.6 0.16 135)` для мощности, голубой `oklch(0.6 0.12 225)` для ветра, янтарный для предупреждений, фиолетовый для LLM.

## 7. Репозиторий

```
agent/      граф LangGraph, промпты, инструменты
weather/    адаптеры Open-Meteo, кэш по as_of
features/   MOS, плотность воздуха, лаги
models/     LightGBM-квантили, кривая мощности
backtest/   replay и метрики
api/        FastAPI: /forecast?as_of=…, /report, /metrics
ui/         дашборд
data/       SCADA и архив NWP
README.md   запуск и сценарий демо
```

```bash
make setup                                      # зависимости и .env (ключ LLM)
make fetch-weather                              # архив прогнозов на каждую T
make train                                      # обучение на данных до 31.01.2026
make replay START=2026-01-31 END=2026-02-27     # 28 запусков агента и метрики
docker compose up                               # API и дашборд на :8000
```

Воспроизводимость: фиксированные сиды, закэшированная погода в репозитории или скрипте, версии зависимостей, `temperature=0` у LLM.

## 8. План работ

1. Загрузка SCADA, чистка, кривая мощности.
2. Архив NWP через Previous Runs API с проверкой `available_at`.
3. Признаки, MOS, LightGBM-квантили, walk-forward.
4. Инструменты с `as_of` и unit-тест на утечку будущего.
5. Граф агента, условный перерасчёт, отчёт на русском.
6. Replay за февраль, метрики, сравнение с базовыми методами.
7. API и подключение дашборда к реальным данным (заменить синтетику в `build()`).
8. README, Docker, сценарий демо.
