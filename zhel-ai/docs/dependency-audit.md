# Проверка зависимостей на уязвимости

## Правило

**Перед каждым мерджем в main зависимости проверяются на известные уязвимости.**
Одной командой:

```bash
make audit
```

Это пункт чеклиста в шаблоне pull request, и та же проверка идет автоматически
в GitHub Actions на каждый pull request.

## Что именно проверяется

| Стек | Инструмент | Что смотрит |
|------|-----------|-------------|
| Python | `pip-audit` | зафиксированные версии из `backend/uv.lock`, без dev-зависимостей |
| npm | `npm audit --omit=dev` | `frontend/package.json`, когда он появится |

Скрипт [../scripts/audit-deps.sh](../scripts/audit-deps.sh) запускает оба шага.
Пока папки `frontend/` нет, npm-часть сообщает, что проверять нечего, и не падает.

Python-часть работает по выгрузке из lock-файла, а не по установленному окружению.
Так проверяются именно те версии, которые попадут в образ, а не то, что случайно
стоит на машине разработчика.

## Когда и как запускать

- **Локально перед PR**: `make audit`, либо сразу `make check`, который прогоняет
  линтер, тесты и аудит.
- **В pull request**: workflow `.github/workflows/audit.yml`. Он же прогоняется по
  расписанию раз в сутки, чтобы свежая уязвимость не ждала следующего PR.
- Аудит вынесен в отдельный workflow, а не в `ci.yml`, намеренно. Новая уязвимость
  в чужой библиотеке появляется без наших изменений, и она не должна красить бейдж CI.
  При этом в pull request она видна.

## Что делать с находкой

Не мерджим, пока не разобрались. Порядок:

1. Посмотреть, есть ли исправленная версия. Обычно да, и тогда достаточно поднять
   версию: `uv --project backend lock --upgrade-package <имя>`, затем `make audit`
   и `make test`.
2. Если исправления нет, понять, затрагивает ли уязвимость наш код. Уязвимость
   в функции, которую мы не вызываем, не блокирует работу.
3. Осознанно принятый риск фиксируется: строка в `SECURITY.md` в разделе о том,
   чего пока нет, и причина в описании pull request. Молча игнорировать нельзя,
   иначе документация начнет расходиться с реальностью.

Отдельно: `pip-audit` запускается с флагом `--strict`, поэтому падает и в том случае,
когда для какого-то пакета не удалось проверить уязвимости. Это сделано намеренно,
чтобы «не смогли проверить» не выглядело как «уязвимостей нет».

## Чего эта проверка не делает

- Не проверяет образ Docker на уязвимости системных пакетов. При необходимости это
  делается вручную: `docker scout quickview hackalem-main-backend`.
- Не проверяет наш собственный код, только сторонние библиотеки. За свой код отвечают
  тесты, линтер и меры из [../SECURITY.md](../SECURITY.md).
- Dependabot не подключен, обновления зависимостей не приходят автоматически.
