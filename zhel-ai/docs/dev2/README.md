# dev2

## Зона ответственности

Только модель прогноза: признаки, обучение, квантили P10/P50/P90 и оценка качества.
Модель работает отдельным HTTP-сервисом `ml` со Swagger-контрактом. Данные dev2 сам
не собирает: источник погоды выбирает и готовит dev3, запрос к модели отправляет агент dev1.
Почему сервис, а не пакет внутри backend: [../adr/0006-ml-service.md](../adr/0006-ml-service.md).

## Как идет прогноз

```
агент dev1 ── get_nwp_multi(sources, as_of=T) ──► данные dev3
           ◄── строки погоды, опубликованные до T ──
     │
     ├── POST /predict {issue_time_utc: T, rows} ──► сервис ml, dev2
     ◄── P10/P50/P90 на часы T+1…T+48 по турбинам ──
     │
     ▼
анализ, решение о публикации, файлы выпуска (dev1)
```

`AsOfStore` dev3 (`backend/src/forecast/weather/asof.py`) уже отдает строки в том формате,
который принимает `POST /predict`: `valid_time_utc, source, run_init_utc, available_at_utc,
lead_h, ws80, ws100, ws120, wd100, gust10, t2m, rh2m, psfc`. Агент кладет их в поле `rows`
без преобразований.

## Что делает

- Держит контракт сервиса: `POST /predict`, `GET /model-info`, `GET /metrics`, `GET /health`.
  Описание: [../../ml/openapi.json](../../ml/openapi.json), Swagger на `http://localhost:8010/docs`,
  пояснения и коды ошибок в [../../ml/README.md](../../ml/README.md). Общая схема с backend:
  [../api-contract.md](../api-contract.md).
- Обучает квантильную модель на LightGBM, по бустеру на P10, P50 и P90, на архивных прогнозах
  погоды той же заблаговременности, что и при работе. Обучение ведется отдельной сессией,
  готовая модель кладется в `ml/artifacts/`.
- Считает качество на отложенном периоде и отдает его через `GET /metrics`.
- Пока обученной модели нет, сервис отвечает по паспортной кривой GW109, `/health` показывает
  `degraded`, в ответе есть предупреждение `BASELINE_MODEL`.

## Что нужно от других

- **dev3.** Погода на момент прогноза через `AsOfStore.get_nwp` и `get_nwp_multi`: для каждого
  выпуска при работе и для каждого исторического выпуска при обучении. История турбин
  `load_scada()` с флагами очистки: это цель обучения. Какие модели погоды нужны модели,
  она объявляет в `GET /model-info`, поле `inputs.sources`.
- **dev1.** Шаг агента `run_model` вызывает `POST /predict` с таймаутом `ML_SERVICE_TIMEOUT`.
  При таймауте или `5xx` агент уходит на запасной прогноз и помечает выпуск `degraded`.
  Доли от номинала переводятся в МВт через `capacity_mw` из ответа.

## Файлы и модули

- `ml/src/ml_service/schemas.py` — контракт: Pydantic-схемы запроса и ответа, из них строится Swagger.
- `ml/src/ml_service/main.py` — приложение FastAPI и эндпоинты.
- `ml/src/ml_service/service.py` — прогноз по запросу: проверка входа, вызов модели, калибровка интервала.
- `ml/src/ml_service/frame.py` — строки погоды в таблицу «час × признак». `build_frame_from_rows`
  одна и та же при обучении и при прогнозе.
- `ml/src/ml_service/predictors/` — модели за одним интерфейсом, `baseline.py` — паспортная кривая.
- `ml/artifacts/` — обученная модель, `model_info.json`, `metrics.json`.
- `ml/openapi.json` — выгрузка контракта. После изменения схем `make ml-openapi`,
  тест `ml/tests/test_openapi.py` падает, если файл разошелся с кодом.
- Тесты в `ml/tests/`, проверки `make ml-test && make ml-lint`.

## Заметки по архитектуре своей части

- Контракт меняется только вместе с dev1: поле, которое backend уже отправляет или читает,
  нельзя переименовать или удалить. Новое необязательное поле добавить можно.
- Сервис сам проверяет утечку: строка с `available_at_utc` позже `issue_time_utc` дает
  422 `LEAKAGE_DETECTED`. Это вторая линия защиты после `AsOfStore`.
- В признаках нет лагов и значений SCADA: в феврале 2026 факта нет. SCADA нужна только
  как цель обучения.
- Состояния между запросами нет: модель читается из `ml/artifacts/` один раз при старте.
- `ml/` — отдельный проект со своими `pyproject.toml`, `uv.lock` и Dockerfile с `libgomp1`
  для LightGBM. Образ backend от LightGBM не зависит.
