# GOAL: что мы должны сдать

Кейс: **Agentic AI для почасового прогноза выработки ВЭС «Шелек»** (2 × Goldwind 2,5 МВт)
на горизонте 24–48 ч с ретро-симуляцией февраля 2026.

Источник требований: бриф кейса [docs/research/wind-forecast-case/00-brief.md](docs/research/wind-forecast-case/00-brief.md).
Зафиксированные решения, контракт между модулями и разбивка на задачи: план в
[issue #2](https://github.com/BAITC-Hacks/hack-5e5a1903-mg-ai/issues/2).
Данные SCADA по двум турбинам лежат в `data/`, период 11.03.2023–31.01.2026, шаг 10 минут.

**Критерий готовности: отмечены все чекбоксы в разделах 1–7.** Раздел 8 опциональный
и в этот критерий не входит.

## 1. Модель на истории

Обязательное требование ТЗ 1: построить модель на исторических данных.

- [ ] SCADA загружается из `data/`, приводится к часовому шагу, есть флаги очистки:
      простои, ограничения, срезы при ветре выше 25 м/с, дубликаты, пропуски (#9)
- [ ] Часовой пояс данных проверен: с 01.03.2024 Алматинская область перешла
      с UTC+6 на UTC+5, сдвиг на границе найден или доказано, что его нет (#10)
- [ ] Два бейзлайна: климатология «час × месяц» и паспортная кривая мощности
      по ветру из прогноза погоды (#11)
- [ ] Признаки строятся одной функцией и для обучения, и для прогноза (#13)
- [ ] В признаках нет лагов и любых значений SCADA: в феврале факта нет,
      и такой признак был бы утечкой
- [ ] Квантильная модель P10/P50/P90 на признаках прогноза погоды, обучающая выборка
      построена через тот же as-of, что и прогноз (#14)
- [ ] Бэктест на январе 2026 в режиме as-of, метрики NMAE и WAPE по корзинам
      заблаговременности 1–24 и 25–48 против обоих бейзлайнов, результат
      в `reports/metrics.json` (#12, #15)

## 2. Погода по координатам, доступная на момент прогноза

Обязательное требование ТЗ 2 и главное ограничение: только архивные прогнозы, которые
были опубликованы к моменту выпуска. Фактическая погода из будущего запрещена.

- [ ] Загрузчик Open-Meteo Single Runs `ecmwf_ifs` по точке 43.6442, 78.5372,
      ветер на 80, 100 и 120 м, кэш прогонов закоммичен (#6)
- [ ] GFS через Previous Runs как запасной источник, когда прогона IFS нет (#8)
- [ ] `get_nwp(source, as_of, valid_times)` отдает только строки с `available_at_utc <= as_of`,
      иначе бросает `LeakageError`; нет прогона — `NoRunAvailable` (#7)
- [ ] As-of считается по времени публикации, а не по времени запуска прогона:
      задержки IFS 7:30 и GFS 7:00 заданы в конфиге
- [ ] Не используются ERA5, Historical Weather и Historical Forecast API
- [ ] На каждый выпуск пишется `manifest.json`: источник, прогон, время доступности,
      заблаговременность (#16)
- [ ] `make leakcheck` автоматически ищет утечки: строки погоды позже `as_of`,
      обращения к запрещенным API, значения SCADA в признаках (#20)

## 3. Почасовой прогноз на 24–48 часов

Обязательное требование ТЗ 3.

- [ ] Выпуск каждый день в 07:00 по Астане (02:00 UTC) накануне целевых суток,
      время выпуска задается в конфиге
- [ ] Каждый выпуск отдает все часы горизонта +1…+48 по каждой турбине
      с колонками `p10`, `p50`, `p90`
- [ ] Всего 28 выпусков: с 31.01.2026 по 27.02.2026
- [ ] Официальный файл: сутки D из выпуска D-1, 672 часа на турбину (#18)

## 4. Агентный цикл с пересчетом при обновлении данных

Обязательное требование ТЗ 4: получение погоды → подготовка данных → запуск модели →
почасовой прогноз → анализ результата → повторный расчет при обновлении входных данных.

- [ ] Агент это детерминированная state machine, шаги названы словами ТЗ:
      `fetch_weather`, `prepare`, `run_model`, `forecast`, `analyze`,
      `recompute_on_update` (#17)
- [ ] Каждое решение агента пишется в журнал `agent_log.jsonl`: что проверил,
      что выбрал, почему
- [ ] Событие «вышел новый прогон погоды» запускает пересчет, а изменение
      относительно прошлого выпуска объясняется в журнале
- [ ] Отказ основного источника переключает агента на запасной, а не роняет выпуск
- [ ] Шаг `analyze` без факта работает как самопроверка: диапазон 0…1, резкие рампы,
      расхождение источников, риск обледенения
- [ ] Всё работает без ключа LLM. Если LLM используется, он выбирает действие
      из белого списка и пишет объяснение, а прогноз считает модель

## Кратко: что от нас требуется

Прототип агентной системы, которая каждый день накануне целевых суток получает
прогноз погоды по координатам ВЭС, строит почасовой прогноз мощности на 48 часов
вперед по двум турбинам, проверяет результат и пересчитывает его, когда выходит
новый прогон погоды. Всё это прогоняется ретроспективно по февралю 2026 так, как если бы
каждый выпуск делался в свой день.

Главное ограничение: на момент каждого выпуска агенту доступны только те прогнозы
погоды, которые к этому времени были опубликованы. Фактическая погода, реанализ и
склейки из первых часов прогонов считаются утечкой будущего и запрещены. Точно так же
запрещены значения SCADA за февраль в признаках: факта у агента нет.

Сдаем работающий офлайн-пайплайн с запуском из командной строки, закоммиченные
результаты, репозиторий, README с инструкцией запуска и краткое описание архитектуры.
Проект должен подняться с чистого клона без сети и без ключей.

Как распределяются 100 баллов:

| Критерий | Баллы |
|---|---|
| Соответствие задаче и работоспособность | 25 |
| Техническая реализация | 25 |
| README и воспроизводимость | 25 |
| Ценность и применимость | 15 |
| Потенциал развития и оригинальность | 10 |

Точность прогноза отдельным критерием не указана. Три четверти оценки дают за то,
что система работает, честно описана и запускается у судьи с первого раза.
Но «работает» для энергетика значит «лучше бейзлайна», поэтому метрики против
бейзлайнов обязательны.
