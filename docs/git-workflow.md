# Git-флоу

## Правило

Каждый разработчик берет фичу и пилит ее в своей ветке. **В `main` напрямую не пушим
и не коммитим, попасть туда можно только мерджем ветки через pull request.**

Ветка под фичу поднимается **в отдельном worktree** со своим слотом портов,
см. [worktrees.md](worktrees.md).

## Как запрет на main обеспечен

Это не только договоренность, запрет включен тремя механизмами.

| Механизм | Что не дает сделать | Где |
|----------|---------------------|-----|
| Хук `no-commit-to-branch` | создать коммит, находясь на `main` | `.pre-commit-config.yaml` |
| Хук `pre-push` | запушить в `main` из любой ветки | `scripts/no-push-to-main.sh` |
| Защита ветки на GitHub | влить в `main` без pull request, сделать force-push, удалить ветку | `scripts/protect-main.sh` |

Локальные хуки ставятся один раз каждым разработчиком:

```bash
make hooks
```

Защита ветки на GitHub включается один раз на репозиторий, когда он появится:

```bash
make protect-main
```

Серверное правило требует зеленый CI и pull request, но **не требует одобрения
ревьюеров**: ноль обязательных approve, как мы и договорились. Автор мерджит сам.

Локальный хук можно осознанно обойти через `PROTECTED_BRANCH_OVERRIDE=1 git push`.
Это оставлено на случай, когда защита ветки еще не включена, а в `main` нужно положить
самый первый коммит. Серверное правило так не обходится.

## Проверка уязвимостей перед мерджем

Перед каждым мерджем прогоняется `make audit`: `pip-audit` по зафиксированным версиям
Python-зависимостей и `npm audit` для frontend, когда он появится. Есть находки —
не мерджим. Порядок разбора: [dependency-audit.md](dependency-audit.md).

Та же проверка идет автоматически в pull request отдельным workflow, чтобы ее нельзя
было просто забыть.

## Название ветки

```
features-dev{1,2,3}-<name>
```

`{1,2,3}` — твой номер из `.dev-notes/me.md`. `<name>` — короткое имя фичи в kebab-case.

Примеры: `features-dev1-auth`, `features-dev2-upload-api`, `features-dev3-chat-ui`.

## Сообщения коммитов

Формат Conventional Commits: `<префикс>(<область>): <что сделано>`.

| Префикс | Когда |
|---------|-------|
| `feat:` | новая функциональность |
| `fix:` | исправление бага |
| `refactor:` | изменение кода без изменения поведения |
| `test:` | добавление или изменение тестов |
| `docs:` | документация |
| `chore:` | конфиги, зависимости, инфраструктура |

Примеры:

```
feat(auth): add JWT token refresh endpoint
fix(auth): reject refresh token on protected routes
test(auth): cover inactive user login
chore(ci): run ruff format check on pull requests
```

Правила: **один коммит — одно логическое изменение**, сообщение в повелительном
наклонении и на английском. Сообщения вида `wip`, `fix`, `update`, `asdf` не годятся:
соревнование на время, и история коммитов читается как отчет о работе.

## Каждый PR привязан к задаче

**В описании каждого PR есть ссылка на задачу в GitHub Issues.** PR, который ничего
не закрывает, не исправляет и не продвигает, не мерджим: по истории должно быть видно,
зачем появилось изменение и какой пункт плана оно выполнило.

| Строка в описании PR | Когда | Что будет с задачей при мердже |
|---|---|---|
| `Closes #N` | задача выполнена целиком | закроется автоматически |
| `Fixes #N` | исправлен баг, описанный в задаче | закроется автоматически |
| `Refs #N` | сделана часть работы по задаче | останется открытой |

Если подходящей задачи нет, сначала заводим ее, и только потом открываем PR:

```bash
gh issue create --label dev2 --title "[dev2] Что делаем" --body "Зачем и что сделать"
```

Ключевое слово пишется в поле «Задача» шаблона PR. Одна строка на задачу:
PR может закрывать одну задачу и продвигать другую.

## Порядок работы

```bash
git worktree add ../hackalem-worktrees/features-dev1-auth -b features-dev1-auth
cd ../hackalem-worktrees/features-dev1-auth
cp ../../HACKALEM\ AI/.env .env      # и поменять слот портов на свободный
docker compose up -d --build
# пилим фичу, коммитим
make lint && make test               # обязательно перед пушем
make audit                           # уязвимости в зависимостях
git push -u origin features-dev1-auth
gh pr create --base main --fill      # в описании: Closes #N, Fixes #N или Refs #N
gh pr merge --squash --delete-branch
```

- Фича доделана → создаем **PR в `main`** со ссылкой на задачу и мерджим.
- **Ревью остальных разработчиков не нужно.** Мерджит сам автор, сразу после создания PR.
  Хакатон, ждать никого не надо.
- Шаблон PR подставляется автоматически из `.github/pull_request_template.md`,
  в нем есть чеклист.
- CI прогоняет линтер, проверку формата, тесты и сборку образа. Мерджить с красным
  CI нельзя: на сдаче красный прогон выглядит хуже, чем его отсутствие.
- После мерджа **сразу** сносим worktree и освобождаем порты, [worktrees.md](worktrees.md).
- Перед пушем проверить, что не уезжают секреты: `.env`, ключи, токены
  (см. [../rules/README.md](../rules/README.md)).
- Если фича задевает чужую зону, пишем об этом в свой файл `.dev-notes/dev{N}.md`.
- Перед PR подтянуть `main`, чтобы поймать конфликты у себя, а не в PR:

```bash
git fetch origin
git rebase origin/main
```
