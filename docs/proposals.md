# Предложения по стеку

**Ничто из этого документа не внедрено и не внедряется без явного старта от команды.**

Это реестр инструментов, которые хорошо подошли бы проекту, с описанием того, когда
именно они понадобятся и чем мы за них заплатим. Пока пункт не одобрен, в коде,
зависимостях и compose его нет.

## Как этим пользоваться

Правило для всех, включая ИИ-агентов:

1. Задача упирается в ограничение, которое решает известный инструмент — **предложить**
   его и объяснить, почему он подходит. Молчать нельзя: непредложенное решение это
   тоже ошибка.
2. Предложение попадает сюда: новый пункт либо уточнение существующего.
3. **Не добавлять** зависимость, сервис, конфиг или папку, пока команда не сказала
   «делаем». Ответ «интересно» стартом не считается.
4. Одобрили — пишем ADR в [adr/](adr/), потом код, потом обновляем
   [ARCHITECTURE.md](ARCHITECTURE.md), и пункт переезжает в раздел «Одобрено».
5. Отклонили — пункт остается здесь со статусом «отклонено» и причиной, чтобы
   через два часа не предлагать то же самое снова.

Статусы: `предложено`, `одобрено`, `отклонено`.

## nginx как обратный прокси и балансировщик

**Статус:** предложено. Не внедрять без старта.

**Когда понадобится.** Как только backend перестает справляться одним контейнером,
либо появляется frontend, который надо отдавать с того же адреса, либо нужен HTTPS
с одним сертификатом на всё.

**Что дает.** Одна точка входа вместо двух портов. Балансировка между репликами
backend. Раздача собранного frontend как статики. Возможность добавить ограничение
частоты запросов и таймауты на уровне прокси, не трогая приложение.

**Почему мы к этому готовы.** Приложение уже без состояния, реплики взаимозаменяемы.
`root_path="/api"` выставлен, поэтому за прокси пути не поедут. Healthcheck у backend
уже есть, балансировщику будет по чему понимать готовность.

**Как это будет выглядеть.** Сервис `proxy` в compose, backend перестает публиковать
порт наружу и масштабируется репликами:

```nginx
upstream backend {
    server backend:8000;   # docker DNS вернет все реплики сервиса
    keepalive 32;
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    location / {
        root /usr/share/nginx/html;   # собранный frontend
        try_files $uri /index.html;
    }
}
```

Реплики поднимаются так: `docker compose up -d --scale backend=3`.

**Чем платим.** Еще один сервис и конфиг-файл. Порты в `.env` меняют смысл: снаружи
остается один порт прокси, а слоты портов из [worktrees.md](worktrees.md) придется
пересмотреть. Локальная отладка становится на один слой длиннее.

**Оценка.** Делать, когда появится frontend или реальная нагрузка. Раньше это лишний
слой, который усложнит запуск для судьи.

## Redis

**Статус:** предложено. Не внедрять без старта.

Самый вероятный следующий сервис: он закрывает сразу четыре наших ограничения,
и все четыре растут из правила «никакого состояния в процессе».

**Что именно он решает у нас.**

| Проблема сейчас | Что дает Redis |
|---|---|
| Refresh-токен выдается, но отозвать его нечем, эндпоинта обмена нет | Список отозванных токенов с истечением по TTL, тогда logout и отзыв становятся возможны |
| Нет ограничения частоты попыток входа, брутфорс ничем не сдерживается | Счетчик попыток по ключу, общий для всех реплик |
| Повторные запросы к LLM будут считаться заново, это время и деньги | Кеш ответов по хешу запроса с TTL |
| Долгие операции держат HTTP-соединение | Очередь задач для фонового воркера |

**Почему он тут хорошо подходит.** Все четыре задачи это короткоживущие данные
с естественным сроком жизни, которые нужны всем репликам одновременно. Кидать их
в PostgreSQL можно, но для счетчиков и кеша это неоправданная нагрузка на основную
базу, а TTL пришлось бы изобретать руками.

**Чем платим.** Еще один сервис в compose и еще одна точка отказа: код должен
корректно работать, когда Redis недоступен, иначе падение кеша уронит вход в систему.
Плюс библиотека и переменные окружения.

**Оценка.** Брать, когда понадобится первое из четырех, а не «на будущее». Скорее
всего первым станет кеш ответов LLM.

## Фоновый воркер для долгих задач

**Статус:** предложено. Не внедрять без старта.

**Когда понадобится.** Если обращение к модели или обработка файла занимает больше
нескольких секунд. Держать HTTP-запрос открытым все это время нельзя: воркеры
gunicorn закончатся, и сервис перестанет отвечать целиком.

**Что дает.** Эндпоинт принимает задачу и сразу отдает идентификатор, обработка идет
отдельным процессом, клиент опрашивает статус. Отказ модели не превращается в
оборванный запрос.

**Варианты.** ARQ проще и работает на том же Redis. Celery мощнее, но тяжелее
в настройке. Для хакатона ARQ уместнее.

**Чем платим.** Зависит от Redis, плюс еще один контейнер и асинхронный контракт
в API, который усложняет frontend.

## Объектное хранилище

**Статус:** предложено. Не внедрять без старта.

**Когда понадобится.** Если кейс подразумевает загрузку файлов. Складывать их в
файловую систему контейнера нельзя: данные исчезнут при пересоздании и не будут
видны другим репликам.

**Что дает.** Файлы лежат отдельно от приложения, в БД хранится только ссылка.

**Варианты.** MinIO в compose для локальной работы, совместимый с S3 API.

**Чем платим.** Сервис, том и код работы с presigned-ссылками.

## pgvector

**Статус:** предложено. Не внедрять без старта.

**Когда понадобится.** Если кейс требует семантического поиска или ответов по
собственным документам.

**Что дает.** Векторный поиск прямо в PostgreSQL, без отдельной векторной базы.
Образ меняется на `pgvector/pgvector`, схема на одно поле и индекс.

**Почему именно он.** Отдельная векторная база это плюс один сервис. При наших
объемах данных за пять часов PostgreSQL с расширением закроет задачу целиком.

**Чем платим.** Смена образа БД и миграция с созданием расширения.

## Идентификатор запроса в логах

**Статус:** предложено. Не внедрять без старта.

**Когда понадобится.** Когда трое разработчиков начнут разбирать чужую ошибку по логам.

**Что дает.** Middleware присваивает каждому запросу идентификатор, кладет его в логи
и возвращает в заголовке ответа. По одному идентификатору из ответа собирается вся
история запроса.

**Чем платим.** Около двадцати строк кода и одна настройка логгера. Самое дешевое
предложение в этом списке.
