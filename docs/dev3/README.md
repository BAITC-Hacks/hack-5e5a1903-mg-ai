# dev3

## Зона ответственности

Все входные данные прогноза: погода, история турбин (SCADA), часовой пояс, сборка таблиц
для модели (#2). Пакеты `backend/src/forecast/weather/` и `backend/src/forecast/dataset/`.
Источник погоды выбирает dev3. Строки погоды на момент прогноза агент dev1 передает
в ML-сервис dev2 как есть, поэтому их колонки совпадают с `rows` в `POST /predict`
([../../ml/openapi.json](../../ml/openapi.json)).

## Что делает

- Загружает архивные прогоны ECMWF IFS HRES 9 км из Open-Meteo Single Runs и хранит их кэш (#6).
- Отдает погоду строго на момент прогноза, без прогонов, опубликованных позже (#7).
- Отдает историю турбин по часам в UTC с флагами очистки (#9), пояс SCADA проверен (#10).
- Отдает всё это backend по HTTP: сервис погоды (#46), контракт в [weather-service.md](weather-service.md)
  и [weather-openapi.json](weather-openapi.json).

## Файлы и модули

- `backend/src/forecast/weather/sources.py` — реестр источников погоды: шаг прогонов,
  задержка публикации и ее обоснование, папка кэша. После #5 переедет в конфиг.
- `backend/src/forecast/weather/fetch_ifs.py` — загрузчик IFS (#6), кэш `data/nwp/ifs/`
  с `SHA256SUMS` и `gaps.csv`. Тесты без сети: `backend/tests/forecast/test_fetch_ifs.py`.
- `backend/src/forecast/weather/asof.py` — `AsOfStore`: `get_nwp`, `get_nwp_multi`,
  `run_events`, ошибки `LeakageError` и `NoRunAvailable`, проверка `check_no_leakage`.
- `backend/src/forecast/weather/manifest.py` — паспорт выпуска (#16): `build_manifest`
  и `write_manifest`, схема в docstring модуля. Подписывает выпуск, только если ни одна
  строка погоды не вышла позже `as_of` и `available_at_utc` не раньше задержки из
  `sources.py`; сверяет кэш с `SHA256SUMS`, пишет `missing_sources` для ансамбля (#39).
  Тесты: `backend/tests/forecast/test_manifest.py`.
- `backend/src/forecast/dataset/scada.py` — `load_scada()`: ScadaHistory из #2, обе турбины
  в длинном формате, часовой шаг, `time_utc`, флаги очистки (#9).
- `backend/src/forecast/dataset/config.py` — пути (`DATA_DIR`, `REPORTS_DIR`), правило пояса
  `SCADA_UTC_OFFSET_H`, паспорт GW109 и пороги флагов.
- `backend/src/forecast/dataset/scada_summary.py` — генерирует `reports/scada_summary.md`.
- `backend/src/weather_service/` — HTTP-сервис погоды поверх `AsOfStore` и `load_scada()`:
  `/health`, `/sources`, `/nwp`, `/runs`, `/scada`. Тесты: `backend/tests/weather_service/`.
- `backend/src/analysis/tz_check.py` — проверка пояса SCADA (#10), генерирует `reports/tz_check.md`.
  Использует ERA5 как дополнительную диагностику, поэтому лежит вне `src/forecast`.
- Тесты: `backend/tests/forecast/test_asof.py` (синтетический кэш в `synthetic_nwp.py`),
  `backend/tests/forecast/test_scada.py`, `backend/tests/test_tz_check.py`.

Отчеты по SCADA пересобираются из папки `backend`, сеть не нужна:

```bash
uv run python -m src.forecast.dataset.scada_summary
uv run python -m src.analysis.tz_check
```

## Заметки по архитектуре своей части

- Прогон доступен в момент `run_init_utc + задержка источника`. Задержки выбраны
  консервативно: лишний час стоит немного точности, недостающий час — это утечка.
- Для каждого часа берется самый свежий доступный прогон. Если хоть для одного
  запрошенного часа прогона нет, `get_nwp` бросает `NoRunAvailable`, а не отдает неполную таблицу.
- Прогоны вне шага источника (например 06z и 18z у GEM) отбрасываются при загрузке
  с предупреждением в логе.
- Кэш читается один раз на экземпляр `AsOfStore`, а не на уровне модуля.
- Время SCADA — UTC+6 на всём периоде, перехода на UTC+5 01.03.2024 в данных нет.
- Час SCADA в `load_scada()` — среднее записей hh:00…hh:50 с меткой начала часа. Для сравнения
  с мгновенными значениями погоды (`tz_check`) часы центрируются на hh:00.
- Флаги: `frozen_sensor`, `cut_out`, `icing`, `downtime`, `curtailment`, пустая строка для чистого часа.
  Один флаг на час, по приоритету из `FLAG_PRIORITY`.

## Погода IFS из Single Runs (#6)

Обновить кэш из папки `backend`, нужна сеть (около 1 500 запросов, 20 минут):

```bash
uv run python -m src.forecast.weather.fetch_ifs                          # весь период
uv run python -m src.forecast.weather.fetch_ifs --start 2024-03-15 --end 2024-03-17
uv run python -m src.forecast.weather.fetch_ifs --retry-gaps             # перезапросить всё из gaps.csv
```

**Почему Single Runs `ecmwf_ifs`.** API отдает прогон по точному времени запуска,
поэтому у каждого значения известен прогон, а время доступности считается как запуск
плюс задержка из `sources.py`. По сверке с SCADA IFS точнее GFS и GEM
(`reports/weather_vs_scada.md`).

**Какие прогоны.** 12z и 18z каждого дня с 15.03.2024 для обучения: выпуск в 02:00 UTC
видит 18z предыдущего дня, опубликованный в 01:30, а без него 12z. С 01.02.2026 качаются
все четыре прогона суток, по ним агент пересчитывает февральские выпуски. У каждого
прогона первые 72 часа.

**Задержка публикации 7:30** (`sources.py`). Для февраля 2026 она консервативна: шаги
0–90 всех четырех прогонов ECMWF рассылает к +6:12, Open-Meteo по метаданным отдал
прогон 00z 23.09.2026 через 7,0 ч. Для истории 2024–2025 это допущение «доступность
как сейчас»: до 01.10.2025 IFS 9 км открыто в реальном времени не публиковался,
а открытые данные 0,25° шли на 2 ч позже, шаг 72 около +8:12. С честной исторической
задержкой обучение шло бы на 12z, а симуляция на 18z, и заблаговременности разошлись бы.

**Пробелы в архиве.** Проверено полной загрузкой, всё перечислено в `gaps.csv`:

- до 05.08.2024 включительно в Single Runs нет прогонов 18z IFS. Это 144 прогона,
  на их месте as-of возьмет 12z предыдущего дня: заблаговременность до 62 ч из 71,
  горизонт +48 ч закрыт. 00z их не заменит: он публикуется в 07:30 UTC, позже выпуска.
  Прогоны 06z до февраля 2026 не качаются, в архиве их нет как минимум до 06.08.2024;
- 04.08–09.08.2025 архив Open-Meteo поврежден: нет прогонов 12z 08.08, 18z 04.08
  и 18z 07.08, а у девяти прогонов этих дней часть переменных пуста, у шести из них
  пуст ветер на всех высотах. Повторный запрос отдает то же самое. Строки без ветра
  `AsOfStore` не отдает и берет на эти часы прошлый прогон с ветром, но на весь горизонт
  его не хватает: выпуски 05, 06, 08 и 09.08.2025 получают `NoRunAvailable`, у выпусков
  07.08 и 10.08 пусты `t2m`, `rh2m` и `psfc`;
- январь и февраль 2026, на которых идут бэктест и симуляция, полные.

**Формат кэша** совпадает с кэшем Previous Runs (#8), поэтому `AsOfStore` читает его
без изменений:

- `data/nwp/ifs/<yyyy-mm>.csv.gz`, месяц по времени запуска прогона;
- колонки `run_init_utc`, `valid_time_utc` и восемь переменных с именами как в API,
  время в виде `2024-03-15T12:00:00Z`;
- у каждого прогона ровно 72 строки, часы 0…71, пустое значение — пустая ячейка;
- сортировка по `(run_init_utc, valid_time_utc)`, числа `%.2f`, переводы строк `\n`,
  gzip с `mtime=0`: повторная запись дает побайтно тот же файл.

`gaps.csv` перечисляет недоступные прогоны (`variable=*`, `reason=modelRunUnavailable`)
и пустые значения внутри скачанных прогонов (`reason=null`). Пустой порыв на нулевом часу
прогона ожидаем, это максимум за прошедший час, поэтому в список он не попадает.

**Колонки для dev2.** IFS отдает всё из PredictRequest, кроме `ws10`: ветер на 10 м не
качается. `gust10` пуст на нулевом часу прогона, а он всегда раньше выпуска и в горизонт
не входит. Исключение — поврежденный архив августа 2025 из списка выше. Пустое значение
приходит как NaN, а `WeatherRow` принимает только `null`, поэтому при отправке в `ml`
NaN переводится в `null`.
