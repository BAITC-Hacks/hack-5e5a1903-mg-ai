# dev1

## Зона ответственности

Агент и центральный backend (#2). Агент принимает запрос на прогноз, берет погоду на момент
выпуска у dev3, отправляет ее в ML-сервис dev2 (`POST /predict`), анализирует ответ,
решает о публикации и пишет файлы выпуска. Backend отдает результат интерфейсу
по [../api-contract.md](../api-contract.md). Итоговая интеграция и README тоже за dev1.

## Что делает

- Цикл агента поверх соседей: погода на момент выпуска от dev3, квантили от ML-сервиса dev2,
  сборка выпуска, самопроверка, пересчет по новому прогону.
- Держит границу: таймауты, коды отказа, проверка ответов схемой, журнал решений.
- Пока соседи не отвечают, эндпоинты продолжают работать на демонстрационных числах
  с честной пометкой `data_source="stub"`.

## Файлы и модули

- `backend/src/modules/forecast/orchestrator.py` — цикл агента и **единственная точка
  переключения** живого выпуска и заглушки. Шаги названы словами ТЗ: `fetch_weather`,
  `prepare`, `run_model`, `forecast`, `analyze`, `recompute_on_update`.
- `backend/src/modules/forecast/clients/` — границы: `weather.py` (сервис dev3 по HTTP,
  тот же кэш пакетом в процессе и шлюз между ними), `ml.py` (ML-сервис dev2),
  `schemas.py` (формы ответов соседей), `base.py` (таймауты и коды отказа).
- `backend/src/modules/forecast/analyze.py` — чистые проверки: годность прогона,
  флаги риска, расхождение источников, существенность изменения версии.
- `backend/src/modules/forecast/decisions.py` — журнал решений, имена шагов и коды причин.
- `backend/src/modules/forecast/config.py` — факты кейса: объект, режим выпуска, источники.
- `backend/src/modules/forecast/service.py` — демонстрационные числа и общие предметные
  функции: кривая мощности, KPI, заявка диспетчера.
- Тесты: `backend/tests/test_forecast_gateway.py` (граница и отказы, соседи подделаны),
  `backend/tests/test_forecast_agent.py` (правила агента), `backend/tests/test_forecast_api.py`
  (формы ответов).

## Заметки по архитектуре своей части

- Правила и пороги агента лежат в одном месте, в `analyze.py`: их же использует
  демонстрационный выпуск, чтобы не появилось двух расходящихся наборов правил.
- Отказ соседа это не 500 и не пустой экран: код причины уходит в журнал решений,
  а выпуск собирается заглушкой. Утечка будущего — единственное исключение, ее
  показывают ошибкой `WEATHER_LEAKAGE`, а не прячут за демонстрацией.
- Состояния в памяти процесса нет: журнал, клиенты и хранилище погоды создаются
  на каждый запрос, реплики backend остаются взаимозаменяемыми.
- Квантили считает модель. Бэкенд их не правит и не досчитывает, МВт берутся
  умножением доли на `capacity_mw` из ответа модели.
