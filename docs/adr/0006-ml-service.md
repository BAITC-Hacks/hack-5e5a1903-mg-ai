# 0006. Модель прогноза — отдельный сервис с HTTP-контрактом

**Статус:** принято 2026-09-23, решение dev2.

## Контекст

dev2 отвечает только за модель. Агент (dev1) и данные (dev3) должны работать с ней через
стабильный контракт, не зная ее устройства. Модель обучается на LightGBM, а LightGBM
в образе `python:3.12-slim` требует системный `libgomp1`, которого в образе backend нет.
По этой причине в [0005](0005-ml-stack.md) LightGBM был отклонен для backend.

## Решение

- Сервис `ml` в `docker-compose.yml`, собственный проект `ml/` со своим `uv.lock`
  и Dockerfile, в котором стоит `libgomp1`.
- FastAPI, эндпоинты `GET /health`, `POST /v1/predict`, `GET /v1/model`,
  `GET /v1/model/backtest`. Контракт — `ml/openapi.json`, он генерируется из Pydantic-схем,
  тест сверяет файл с кодом.
- Вход — строки прогноза погоды «час × модель погоды» с временем публикации прогона.
  Сервис сам отклоняет прогоны, доступные позже момента прогноза (`LEAKAGE_DETECTED`).
- Выход — P10/P50/P90 долей от номинала для T1, T2 и станции.
- Модель загружается из `ml/artifacts/` один раз при старте. Пока обученной модели нет,
  сервис отвечает по паспортной кривой мощности и сообщает `degraded`.

## Последствия

Плюсы: зоны разделены контрактом, LightGBM не трогает образ backend, Swagger описывает
вход и выход, backend подключается к заглушке до конца обучения.

Минусы: еще один образ и сервис в compose, сборка стека дольше. Вызов идет по сети внутри
compose, поэтому на стороне агента обязательны таймаут `ML_SERVICE_TIMEOUT_S` и запасной
прогноз. В слотах worktree появился порт `ML_PORT`. Аудит зависимостей проверяет два `uv.lock`.

## Отклоненная альтернатива

Вызов модели внутри процесса backend, как было в первой версии плана (issue #2): запуск
проще, но LightGBM потребовал бы правки образа backend, а зоны dev1 и dev2 смешались бы.
