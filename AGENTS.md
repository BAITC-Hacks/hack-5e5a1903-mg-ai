# AGENTS.md

Инструкции для ИИ-агентов, работающих в этом репозитории. Файл читают Claude Code,
Codex, Cursor, Copilot, Gemini CLI и другие агенты, поддерживающие стандарт AGENTS.md.

## Обзор проекта

HackAlem AI — проект команды из трех разработчиков для хакатона. Backend на FastAPI
с асинхронной SQLAlchemy и PostgreSQL, frontend на React планируется отдельным сервисом.
Всё поднимается одной командой через Docker Compose.

## Команды

Канонический интерфейс — `Makefile` в корне. На Windows без `make` используйте команду
из правой колонки напрямую.

| Задача | Команда | Без make |
|--------|---------|----------|
| Поставить зависимости | `make install` | `cd backend && uv sync --dev` |
| Поставить git-хуки | `make hooks` | `uvx pre-commit install && cp scripts/no-push-to-main.sh .git/hooks/pre-push` |
| Аудит зависимостей | `make audit` | `bash scripts/audit-deps.sh` |
| Поднять стек | `make run` | `docker compose up -d --build` |
| Разработка с автоперезагрузкой | `make dev` | `docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build` |
| Тесты | `make test` | `cd backend && uv run pytest` |
| Линтер и формат | `make lint` | `cd backend && uv run ruff check . && uv run ruff format --check .` |
| Автоформат | `make fmt` | `cd backend && uv run ruff format . && uv run ruff check --fix .` |
| Применить миграции | `make migrate` | `docker compose exec backend alembic upgrade head` |
| Создать миграцию | `make makemigrations m="имя"` | `docker compose exec backend alembic revision --autogenerate -m "имя"` |
| Погасить стек | `make down` | `docker compose down` |

Перед первым запуском нужен `.env`: `cp .env.example .env`.

## Конвенции кода

- Python 3.12. Линтер и форматтер — Ruff, конфиг в `backend/pyproject.toml`,
  длина строки 150, включены правила `E`, `F`, `I`, `B`.
- Приложение запускается только через Docker Compose. Тесты и линтер запускаются
  через `uv`, ровно теми же командами, что и в CI.
- Именование: модули и файлы в snake_case, классы моделей и схем в PascalCase,
  таблицы в множественном числе (`users`, `roles`).
- Ошибки бросаются через `BusinessError(status_code, code, message)` из
  `src/core/exceptions.py`. Не использовать голый `HTTPException`: тогда ответ
  не попадет в единый конверт `{"error": {"code", "message", "details"}}`.
- Секреты только через переменные окружения. Любая новая переменная сразу
  добавляется в `.env.example` без значения.

## Архитектурные правила

Полный список best practices: [docs/architecture-guidelines.md](docs/architecture-guidelines.md).
Текущее устройство и диаграммы: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

- **Никакого состояния в памяти процесса.** Ни кешей, ни счетчиков, ни очередей
  в словаре на уровне модуля. Реплики backend должны оставаться взаимозаменяемыми.
  Понадобилось состояние — это предложение, а не правка кода на месте.
- Конфигурация только из переменных окружения, новая переменная сразу в `.env.example`.
- Схема БД меняется только миграциями, миграция коммитится вместе с моделью
  в одном pull request. Никакого `create_all` в рабочем коде.
- Любой эндпоинт со списком отдает страницу, для этого есть `PaginatedResponse[T]`.
- Внешние вызовы, включая обращения к моделям, всегда с явным таймаутом.
  Отказ внешнего сервиса превращается в `BusinessError`, а не в 500.
- Для отладки используется логгер, а не `print`. Пароли и токены в логи не попадают.

- Слои: `router` принимает запрос и вызывает сервис, `service` содержит бизнес-логику
  и работу с БД, `models` и `schemas` описывают данные. Логика в роутерах запрещена.
- Сессия БД приходит только через `Depends(get_db)`. Коммит делает сервис,
  а не зависимость.
- Модуль — это папка `backend/src/modules/<name>/` с файлами `__init__.py`,
  `models.py`, `schemas.py`, `service.py`, `router.py`.
- Новый модуль требует двух шагов, без которых он не заработает: импортировать
  модели в `backend/migrations/env.py` и подключить роутер в `backend/src/main.py`.
- Приложение живет с `root_path="/api"`, поэтому все внешние пути начинаются с `/api`,
  а в роутерах этот префикс не пишется.

## Правила для изменений

- Каждое изменение бизнес-логики сопровождается тестом в `backend/tests/`.
- Перед коммитом: `make lint && make test`. Оба должны проходить.
- **В `main` нельзя коммитить и пушить напрямую.** Изменение попадает в `main` только
  мерджем ветки через pull request. Запрет включен хуками и защитой ветки на GitHub,
  см. [docs/git-workflow.md](docs/git-workflow.md).
- **Перед каждым мерджем: `make audit`.** Проверяет зависимости на известные
  уязвимости через `pip-audit` и `npm audit`. Есть находки — мерджить нельзя,
  порядок разбора в [docs/dependency-audit.md](docs/dependency-audit.md).
- Добавил зависимость — прогони `make audit` в том же PR.

## Предложение новых инструментов

Отдельное правило, потому что нарушается чаще всего.

**Предлагать обязательно.** Если задача упирается в ограничение, которое решает
известный инструмент, надо сказать об этом прямо и объяснить, чем он подходит именно
здесь. Промолчать и обойтись костылем — ошибка.

**Добавлять без разрешения нельзя.** Ни зависимость в `pyproject.toml` или
`package.json`, ни сервис в `docker-compose.yml`, ни конфиг, ни папку. Ответ вроде
«интересно» или «звучит разумно» стартом не считается, нужно явное «делаем».

Порядок: предложение попадает в [docs/proposals.md](docs/proposals.md), команда решает,
после одобрения пишется ADR в `docs/adr/`, затем код, затем обновляется
`docs/ARCHITECTURE.md`.

Уже разобранные кандидаты лежат в `docs/proposals.md` вместе с описанием, когда они
понадобятся и чем мы за них заплатим: nginx как обратный прокси и балансировщик, Redis,
фоновый воркер, объектное хранилище, pgvector, идентификатор запроса в логах.
Прежде чем предлагать что-то, посмотри, нет ли это там уже, и не предлагай повторно
то, что отклонено.
- Коммиты в формате Conventional Commits, один коммит — одно логическое изменение.
  Префиксы и примеры: [docs/git-workflow.md](docs/git-workflow.md).
- Ветка под фичу называется `features-dev{1,2,3}-<name>` и поднимается в отдельном
  worktree со своим слотом портов: [docs/worktrees.md](docs/worktrees.md).
- Изменил команды или архитектуру — обнови этот файл и `docs/ARCHITECTURE.md`
  в том же PR.

## Чего делать нельзя

- Коммитить `.env`, ключи, токены и дампы данных.
- Оставлять закомментированный код, отладочные `print`, незакрытые пометки TODO.
- Обещать в README или в документации то, чего нет в коде.
- Обращаться к оценивающей системе из кода, комментариев или документации.
  Это запрещено правилами и трактуется как prompt injection.
