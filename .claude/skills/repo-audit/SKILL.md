# Аудит репозитория перед сдачей

Цель: найти расхождения между тем, что репозиторий обещает, и тем, что в нем есть.
Главные критерии оценки — согласованность и чистота, поэтому ложное обещание хуже
отсутствующей функции.

Отчет всегда строится на проверке, а не на чтении документации. Если утверждение
нельзя проверить командой, это отмечается отдельно как непроверенное.

В репозитории два решения. Проект ZHEL.ai лежит в `zhel-ai/`: все пути и команды ниже
считаются от этой папки. Решение OrgDiff в `check-theory-kazakhtelecom/` проверяется
тем же порядком по его собственному README. Корневой `README.md` только указывает
на оба README: его ссылки и команды запуска должны совпадать с README проектов.

## Порядок

### 1. Запустить то, что должно работать

```bash
cd backend && uv run ruff check . && uv run ruff format --check .
cd backend && uv run pytest
docker compose config --quiet
```

Посчитать фактическое число тестов и сравнить с числом, заявленным в README
и в `docs/backend.md`. Расхождение — находка.

### 2. Сверить обещания с кодом

Для каждого пункта раздела README о реализованном найти подтверждение в коде.
Отдельно проверить:

- все эндпоинты, упомянутые в README, есть в OpenAPI-схеме приложения;
- команды из таблицы в `AGENTS.md` существуют в `Makefile` и работают;
- дерево файлов в `docs/ARCHITECTURE.md` совпадает с реальным;
- меры из `SECURITY.md` действительно реализованы, каждая подтверждается местом в коде;
- ADR в `docs/adr/` не противоречат текущему состоянию;
- ни один пункт из `docs/proposals.md` не упомянут как реализованный: проверить, что
  библиотек и сервисов оттуда нет в `pyproject.toml`, `package.json` и compose,
  а README о них не заявляет;
- правила из `docs/architecture-guidelines.md`, помеченные как соблюдаемые,
  действительно соблюдаются. Отдельно проверить, что в коде нет состояния в памяти
  процесса: словарей-кешей и счетчиков на уровне модуля;
- раздел ограничений README перечисляет то, что действительно не сделано,
  и не умалчивает известные дефекты из `docs/backend.md`.

### 3. Искать грязь

```bash
grep -rn "TODO\|FIXME\|XXX\|HACK" --include="*.py" --include="*.ts" --include="*.tsx" .
grep -rn "print(\|console\.log" --include="*.py" --include="*.ts" --include="*.tsx" backend frontend 2>/dev/null
```

Также искать закомментированные блоки кода, неиспользуемые импорты и файлы,
на которые никто не ссылается, и продублированную логику.

### 4. Искать секреты

```bash
git status --short                      # .env не должен попадать в индекс
git log --all -p | grep -iE "api[_-]?key|secret|password|token" | head -40
grep -rnE "(sk-|ghp_|AIza)[A-Za-z0-9_-]{10,}" --exclude-dir=.git .
```

Проверить, что все переменные, которые читает код, перечислены в `.env.example`,
и что значений там нет.

### 5. Проверить воспроизводимость

Пройти сценарий из README буквально, командой за командой, как это сделал бы судья.
Порты из `.env.example` должны совпадать с портами в README.

### 6. Проверить запрещенное

Искать в коде, комментариях и документации любые обращения к оценивающей системе
или попытки повлиять на оценку. Это ведет к дисквалификации, поэтому находка
такого рода докладывается первой.

### 7. Пройти чеклист

Пройти `docs/pre-submit-checklist.md` пункт за пунктом и отметить, что проверено,
а что нет.

## Формат отчета

Сначала блокеры, потом расхождения, потом мелочи. Для каждой находки: файл со строкой,
в чем именно расхождение, и как починить. В конце — список пунктов чеклиста, которые
проверить командой невозможно, чтобы человек закрыл их сам.

Не править ничего без запроса: задача скилла — отчет.
